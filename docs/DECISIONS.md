# Decisions

Choices that shaped the project and the reason for each. Newest at the bottom.

| ID | Decision | Why |
|---|---|---|
| D01 | Logistic regression is the Milestone 1 model. | It ties the random forest (AUC 0.835 vs 0.838, a gap one tenth the size of the split-to-split wobble), is well calibrated, and can run in a web page. Revisited in M4. |
| D02 | The app runs in the browser, not on a server. | Nothing to host or keep alive, and it fits the static portfolio. A server version is optional (E28). |
| D03 | Screening cut-off set where at least 85% of true cases are caught (0.24). | A missed case costs more than a follow-up blood test. The 85% figure is a judgment call, replaced by a cost-based choice in M5 (D17). |
| D04 | All eight inputs are kept. | Four inputs score the same (0.833 vs 0.835), but keeping eight lets the app show every contribution and leaves M2 and M3 something to test. |
| D05 | Notebooks are the source of truth and are re-run with `python -m src.run_notebooks`. | Saved outputs can't drift from the code. Shared logic lives in `src/` so notebooks stay short. |
| D06 | Notebook pages for the site are rendered by a small custom script, not nbconvert's default template. | Pages come out at a fraction of the size and carry the portfolio's back bar and no-index tag. |
| D07 | Accuracy is never reported alone. | Always answering "no diabetes" scores 65% while catching nobody. |
| D08 | The page states plainly that this is not a medical tool. | 768 women from one community in the 1980s. It shows method, not a diagnosis. |
| D09 | The published model leaves insulin and skinfold thickness out (six inputs). | Seven ways of handling the gaps score the same (AUC 0.832 to 0.838). Hidden insulin readings can't be guessed back (29% of variation at best), and 53 women change sides of the cut-off depending on the fill. Six inputs score 0.838 against 0.836 for eight, and need two fewer measurements. Insulin is re-tested in M3 (E29). Supersedes D04. |
| D10 | Notebooks 01 to 03 stay as the eight-input Milestone 1 record; the page and app always describe the current model. | Each notebook documents the state of knowledge at its milestone. `reports/metrics.json` keeps the baseline and a separate `current` section so neither goes stale. |
| D11 | The published model is logistic regression with curves for glucose, BMI and age (six inputs, extremes held at the 1st and 99th percentiles). | AUC 0.853 against 0.838 for straight lines, winning 86% of splits and holding on fresh splits. False alarms fall from 194 to 154 at the same 85% catch rate. The model is still a sum of one effect per input, so the app can show each contribution. Costs some sensitivity under 30 (B12). Supersedes D01. |
| D12 | The Explainable Boosting Machine and constrained boosting are not adopted. | Both found similar shapes but scored lower (0.841 and 0.832). With 768 women, a few chosen curves beat a model that has to discover every shape. Revisited in M4. |
| D13 | B10 is closed as improved rather than fully fixed. | Half of women 45 and over have diabetes, so any well-calibrated model flags many of them at a shared cut-off. The fixable part, the wrong age shape, is fixed. Per-band cut-offs are a policy question for M5 (E31). |
| D14 | The page keeps the M3 curves model after the tuned contest. | No model beat it: the tuned curves model's +0.002 AUC is noise (p = 0.36), the stacked ensemble scored 0.849, and every other tuned type scored lower. Switching would change every number on the page for no real gain. |
| D15 | Model comparisons use the corrected resampled t-test, not a plain t-test. | Cross-validation splits share most of their women, so a plain test is overconfident. On curves vs straight lines it gave p = 0.006 where the corrected test gives 0.16. |
| D16 | The M4 contest results are saved in `reports/m4_contest.json` and reloaded. | The nested contest takes several minutes (150 tuned fits per model). The notebook and build reuse the saved run; `run_contest(rerun=True)` repeats it. |
| D17 | The page's default cut-off comes from a stated cost: a missed case is 5 times as bad as a false alarm, so the cut-off is 1 / (1 + 5) = 0.17. The page also offers 2 times (0.33) and 10 times (0.09). | A cut-off should be justified by a cost, not a round target. The old 85% rule (0.28) implied a ratio of about 2.6. Five times is a judgment, so the other two are shown beside it. Supersedes D03. |
| D18 | The model is not rebalanced (no class weights, no SMOTE). | Same ranking, 152 to 154 false alarms to catch 85% of cases either way; a rebalanced model at 0.50 matches the published model at a lower cut-off. Average predicted risk rises from 35% to 43 to 44%, so the risks stop being trustworthy. |
| D19 | One shared cut-off for all ages, not one per age band. | A cut-off per band cost 42 per 100 women against 40 for one shared cut-off (5 times). The risks are well calibrated in every band, and 66 to 118 cases per band is too few to fit a cut-off per band without fitting noise. Fixes B12 without age rules. |
| D20 | The page explains a woman's number with the model's exact contributions, not with SHAP. | The published model is a sum of one effect per input, so each input's contribution can be shown exactly. SHAP reproduces it to within 0.002 log-odds, which verifies the tool; it is used in notebook 08 on a boosted-tree model, where no exact answer exists. |
| D21 | The BMI curve stays. | A bootstrap shows the levelling-off after BMI 30 is real (a steady rise would have multiplied the odds by about 29; the data allow 0.7 to 2.3 times). A straight line for BMI scores 0.006 AUC lower, which could be chance (p = 0.15). Shape is real; benefit for prediction is likely, not proven. |
| D22 | The "What would change this?" box searches glucose and BMI only, one at a time, within 20 mg/dL or 10% of BMI. | Those are the only modifiable inputs the model uses strongly; blood pressure barely matters. The limits keep the answer modest. The box says it explains the model and is not advice, because the model describes patterns, not causes. |
| D23 | The page shows a 95% bootstrap range, described as "about 90%". | 200 refits; in a simulation with known truth the range held the true risk 91.4% of the time (79% to 99% across studies), a little short of its label. The page says what it measures: the model's estimate, not the woman's outcome. |
| D24 | The page adds a conformal call (confident no, confident yes, too uncertain) at the 90% and 80% levels, beside the cost-based flag and not replacing it. | The guarantee held on unseen women over 300 splits (89.9% and 90.8% at 90%; 80.2% and 79.3% at 80%). The cost-based cut-off still decides who gets a follow-up test, since it reflects the cost of a missed case. The conformal call says how much to trust the estimate. |
| D25 | The conformal rule is class by class (Mondrian), and the page's cut-offs come from the out-of-fold risks. | A single rule would guarantee only the average, which the larger healthy group would dominate. Per-class thresholds guarantee each group separately. Cost: a confident "yes" is wrong 25% of the time at 90%, because the guarantee is not about precision. |
| D26 | The outside test uses NHANES 2013 to 2014 women aged 21 and over, with diabetes defined as HbA1c of 6.5% or higher or a doctor's diagnosis. | NHANES is a one-time snapshot, so it cannot give the Pima outcome (diagnosed within five years). HbA1c is a different blood test from the glucose input, so the outcome does not restate an input. Counting glucose of 200 or more as well would raise the share only from 3.9% to 7.1%. The test measures behaviour away from home, not a like-for-like second trial. |
| D27 | The published model and the page's cut-off are not changed or recalibrated after M8. | The ranking carries over (AUC 0.88), so the model stays. The risk numbers are too high on NHANES (25% against 3.9%), but a shift learned there would be wrong for the Pima data the page describes, and with 37 cases it is not well determined. The page says what was tested instead. |
| D28 | The raw NHANES files are not committed; the 961-row table built from them (`data/nhanes_women.csv`) is. | The raw files are 13 MB and public. The small table lets the tests and the site build run without them. `src/external.py` rebuilds the table from the raw files (README lists them). |
| D29 | The model gets no cluster or oddness inputs. | Group membership, distance to group centres and an oddness score each scored slightly below the published model (AUC 0.852, 0.851, 0.852 against 0.853), with ranges that include zero. The groups themselves are unstable and restate age, weight and glucose, which the model already uses. |
| D30 | Odd records are kept in training and recorded, not removed. | Dropping the 15 most unusual women changed AUC by -0.0001 (range -0.003 to +0.002). The unusual 5% scored a little worse in two of three methods but the group is 39 women, so it is weak evidence. Without the original charts there is no basis for calling any record an error. |
| D31 | The page shows a notice when a woman's inputs are beyond the 95th percentile of distance from the typical Pima woman. It does not change the risk. | Unusual women have wider ranges (28 points against 19), and 26% of NHANES women would trigger it. But the risks of the flagged and unflagged NHANES women were both about 25%, so the flag says "less data behind this estimate", not "the risk is X points too high". |
| D32 | GitHub Actions runs the tests and builds the page on every push; re-running all notebooks is a manual job. | The tests and the page build take about a minute and catch the failures that matter (a number drifting, a placeholder left unfilled, a page that no longer builds). The notebooks take much longer and give the same results every time, so running them on every push would mostly burn time. They can be started from the Actions tab when wanted. |
| D33 | MLflow records each evaluation run in a local SQLite database, and a failure to log never stops the evaluation. | The newer file-based store is in maintenance mode, so the database is used. The run record holds the settings, the headline numbers (AUC and its range, calibration slope, caught and flagged shares at the cut-off, outside AUC, coverage) and the Git commit, so a change in any number can be traced to a change in the code. The database stays on the local machine and is not committed. |
| D34 | No Streamlit or FastAPI version (E28 dropped). | The model is a set of lookup tables that the page runs in the browser, so it needs no server, costs nothing to host and cannot go down. A live API would add a server to keep patched without adding anything a reader can see. It is easy to add later if a demonstration of deployment is wanted. |
